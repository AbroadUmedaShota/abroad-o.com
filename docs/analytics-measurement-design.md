## イベントと集計の契約

アプリ内部イベント名は `contact_submit_success`。ブラウザの `/submit` 応答がHTTP成功かつJSON `ok: true` の時だけ、同じ送信IDについて一度発火する。ボタンクリック、フォーム検証通過、サンクスページの直接表示・再読込では発火しない。タイムアウト、5xx、`delivery_review_required`、競合、レート制限も成功に数えない。

#65の既存案との整合を保ち、GA4へはこの内部イベントを推奨イベント `generate_lead` に一対一で変換する案とする。二つを別々のキーイベントにして二重計上しない。GA4の名称・キーイベント指定も承認対象とし、今回コードには追加しない。

同じ内容の通信再試行は送信IDを維持する。ブラウザ内の一度だけ制御に使うIDをGA4へ送らない。ページ再読込・複数端末を含む厳密な一意件数はブラウザ計測だけでは保証しない。正確な受付数は受付台帳で集計し、GA4は同意/通信遮断によって少なくなる参考指標として扱う。メール結果不明でも台帳保存済みの問い合わせは別の運用指標に含める。

GA4へ送る値は固定のフォーム識別子とクエリなしのページパスに限定する案。氏名、メール、電話、住所、会社名、問い合わせ本文、送信ID、入力値のハッシュは送らない。任意クエリ・参照元・自動計測が個人情報を含まないか、ネットワーク上の最終ペイロードで検証する。フォーム自動計測による二重計上を避ける。

## 測定の分担

| 情報源 | 判断に使う指標 | 制約 |
| --- | --- | --- |
| Search Console | Google検索の表示・クリック・クエリ・対象ページ | 所有権/権限確認後、検索流入のみ |
| Bing Webmaster Tools | Bing検索、利用可能ならAI Performanceの引用・参照 | アカウントで利用可能な機能と対象期間を確認、他AI全体に一般化しない |
| GA4 | 同意のある訪問、流入後の動き、受付成功イベント | 権限・PMS承認後に導入。実問い合わせの全件数とは異なる |
| 受付台帳 | 受付数、重複ID、メール結果不明件数 | 個人情報を公開リポジトリやGA4へ転記しない |
| Core Web Vitals / PageSpeed | LCP・INP・CLSと表示性能 | 実利用者データと単発のラボ計測を分け、日時・URL・端末条件を記録。データ不足は未計測 |

## 承認後の検証と切戻し

1. テスト環境で許可時/拒否時、初回/再送、直接サンクス表示、エラー時のイベント数を検証。
2. ブラウザ通信とRealtime/DebugViewで二重計上・PII混入なしを確認。テストは合成データを使用。
3. タグの二重ロード、CSP Report-Only違反、同意状態に反する通信を確認。
4. 独立PRで旧UA撤去とGA4導入をまとめ、公開承認後に反映。
5. 不具合時は新しいGA4送信を無効化する。旧UAの再導入を切戻し策にしない。
